    `deploy.yml` has `timeout-minutes: 30` (blog#3), because GitHub's default
    is 6 hours and this runner deploys every repo in the org. It is a hang
    detector, not a budget: over 23 runs to 2026-09-28 the job took 51s at the
    median and 102s at most. The 867s "tail" blog#3 quoted was queue wait on
    the shared runner (829s of it), which `timeout-minutes` does not count, so
    size a bound from the job's `started_at` to `completed_at`, not from the
    run's. The steps before `docker compose up` have their own bounds
    (checkout 5, build 20), so a hang there fails before the container is
    touched, and the job's bound always leaves 5 minutes for `up` and the
    health check. Raise the build bound and the job bound together; `npm test`
    fails if less than 5 minutes is left. The workflow also runs in one
    `concurrency` group, `production-deploy`, with `cancel-in-progress: false`
    written out (blog#2): a new run waits and never cancels a deploy in
    progress. A new *waiting* run still replaces an older waiting one, and a
    re-run counts as new but builds its own old commit. So re-run only the
    newest Deploy run: re-running an old one can cancel a newer waiting run
    and roll the site back until the next push or 07:05 run.
